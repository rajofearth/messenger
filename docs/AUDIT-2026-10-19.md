# Messenger code, UX and product audit

Date: 2026-10-19. Revision inspected: `774e85d`, version 0.0.5.

## Verdict

Messenger is a capable local Android prototype with more native engineering than its small size suggests. It is not yet a dependable messaging product. The biggest problems are data integrity and integration between otherwise reasonable modules, not an inherently bad stack or a need for a rewrite.

The app has implemented media messages, albums, replies, reactions, forwarding, profiles, stories, simulated calls, Android notification actions, theme handling and APK updates. Several of those features are undermined by lifecycle and persistence mistakes. Stabilizing them will improve the app more than adding another screen.

## Scope and evidence

- Three independent audit agents covered architecture/data, UI/interaction, and native/notification/update/product reliability. Findings were consolidated and duplicates removed.
- Read repository guidance and inspected source. This was a read-only product audit; no application code changed.
- `npm run check` passed, including TypeScript and Expo dependency alignment.
- `npm test` passed: 117 tests, zero failures or skips.
- Additional Node reproductions imported the real `createStore` implementation. They confirmed failed-write success reporting and stale-read cache replacement.
- Contrast calculations confirmed white outgoing-message text at 2.04:1 in light mode and 3.98:1 in dark mode.
- No physical-device session, rendered-screen review, native build, APK gate, security penetration test or performance profile was performed. Code-backed UI findings are not claims of observing the rendered app.
- P1 means fix before trusting user data or publishing another release. P2 means a real behavior/accessibility problem to fix next. P3 means consistency or polish. No remote exploit was established.

### Executed persistence evidence

Two read-only Node reproductions imported `src/data/store.ts`, injected controlled drivers, and asserted the observed defect states.

```text
CONFIRMED: failed write resolved as success; attempts=1
CONFIRMED: in-flight old read replaced newer memory while disk stayed new
```

The first driver always rejected writes. `save()` nevertheless resolved. The second held an old read open, saved a newer value, then released the old read. Subsequent store loads returned the old value while the driver held the new value.

These assertions confirm defects, not passing behavior. Add permanent regression tests that require rejection and preservation of the newer cache value when implementing fixes.

## Notification and native integration

1. **Background conversations still count as visible.** `App.tsx:137-139`, `213-224` uses overlays but not AppState. A simulated reply executing while JS remains alive in the background can be marked read and have its notification suppressed. Use one shared foreground-and-route visibility calculation.
2. **Failed posts count as successful.** `src/notifications/useMessageNotifications.ts:110-114` converts rejection to undefined, then treats undefined as success. `src/features/calls/useCallNotifications.ts:58-73` has the same pattern. Record success only on explicit `posted: true`, with bounded retries.
3. **Disabling notifications can strand an ongoing call notification.** `src/features/calls/useCallNotifications.ts:31-38` exits before cleanup, while `App.tsx:117-127` also disables action consumption. Dismiss existing notifications when posting is disabled; keep cleanup and queued-action recovery independent.
4. **Alerts wait for decorative network work.** Call and message hooks await avatar downloads before posting. See `src/features/calls/useCallNotifications.ts:43-45` and `src/notifications/useMessageNotifications.ts:80-90`. Post immediately with cached/no avatar, then update the same notification when the image arrives.
5. **Privacy changes do not reconcile posted notifications.** `src/notifications/useMessageNotifications.ts:72-78` selects by changed message ID. Turning previews off does not replace existing exposed message bodies; blocking a chat does not remove its existing notification. Reconcile active presentations when privacy state changes.
6. **Incoming calls lack an app-engine timeout.** `src/features/calls/useCalls.ts:20-40` handles dialing/active timers, not incoming expiry. Native notification timeout and app state can disagree. Use a shared deadline and record the outcome once.
7. **Updater redirect policy differs from initial URL policy.** `modules/app-updater/android/src/main/java/expo/modules/appupdater/ApkDownloader.kt:149-152` accepts HTTP redirects despite HTTPS requirements for initial release URLs. Apply the same policy to each redirect. This is not evidence of bypassing Android APK signatures.

## Architecture and code quality

### Keep these decisions

- Expo/React Native is a reasonable choice for this scope. No rewrite is justified by these findings.
- Pure domain functions make message deletion, forwarding, grouping and read-count rules testable.
- Per-thread persistence keys and lazy loading avoid loading every history at startup.
- The repository keeps storage details out of screens. Keep that boundary.
- The notification implementation has serious work behind it: native queueing, generation-aware actions, idempotent reply IDs and an action ledger.
- The updater validates manifests, streams and hashes APKs, uses a restricted FileProvider and relies on Android signature verification for installation.
- Measured APK size and dependency restraint are useful. The documented current APK is 14.27 MiB; this audit did not rebuild or remeasure it.
- Honest prototype and device-testing documentation is better than implying remote calls or production reliability.

### Change these decisions

**Seeds currently participate in live data decisions.** Demo history is used for unloaded conversations, notification history and profile content. This causes actual corruption and misinformation. Initialize explicit demo records once; after initialization, missing/loading/error data must not silently mean demo data.

**Persistence has no trustworthy success contract.** Memory updates, saved-reference markers, disk writes and acknowledgement are treated as interchangeable. Define success at each boundary. A durable reply cannot be acknowledged based on a React state update.

**`useMessenger` owns too many lifecycles.** It combines hydration, persistence, messages, contacts, stories and reply simulation. Extract a thread lifecycle controller and isolate the demo simulator first. Those extractions directly address bugs; splitting by line count alone does not.

**Navigation and visibility are duplicated booleans.** `App.tsx` repeats similar overlay checks for reads, notifications and screen rendering. Introduce a small typed route model and derived visibility. A new navigation dependency is optional, not the first requirement.

**Settings have two owners.** `src/state/useMessenger.ts:61`, `117-125` and `src/features/profile/SettingsPreferences.ts:30-32`, `95-103` hydrate separate representations. Prefer one normalized settings record and explicit update commands.

**Runtime data is trusted because TypeScript says it has a shape.** `src/data/store.ts:71` casts parsed JSON without validating it. Add small record decoders at the repository boundary. Appearance normalization already demonstrates the intended approach.

**The architecture gate measures file size more than architecture.** Keep the 500-line guard, but add enforceable import directions for domain, services, state and features. Existing documented cross-layer imports show where contracts should move.

**"Backend-ready" needs qualification.** Whole-array save methods are a storage substitution point, not a complete messaging protocol. Real messaging needs per-message commands, pagination, subscriptions/incremental sync, client IDs, retries, conflict handling and durable outbox state. Hooks cannot remain entirely unchanged merely by swapping storage drivers.

### Refactor feasibility

| Change | Feasibility | Relative effort | Why |
| --- | --- | --- | --- |
| Centralize thread load/mutate/persist lifecycle | Doable now | Medium | Directly prevents history overwrite and supports meaningful status/retry. |
| Separate simulation from real state commands | Doable now | Small to medium | Prevents seeded/timer behavior from leaking into future transport logic. |
| Shared button states, text tokens and load-state UI | Doable now | Small to medium | Reuses existing controls without a new design-system dependency. |
| Typed route history and derived visibility | Doable now | Medium | Fixes Back behavior and avoids inconsistent read/notification visibility. |
| Replace AsyncStorage wholesale with a database | Doable with prep | Medium to large | Consider when indexed history, pagination and transactional outbox require it. Fix current semantics first. |
| Rewrite app/framework or replace list library | Not worth it now | Large | No evidence those choices caused the current defects or measured runtime problems. |

## What is built, and what is still missing

| Area | Already built | What prevents dependable use |
| --- | --- | --- |
| Conversations | Text/media, replies, reactions, deletion, forwarding and albums | Reliable history mutation, durable attachments, loading/retry, drafts and later delivery state |
| Android integration | Native notification queue/actions, keyboard media, local camera preview and live theme support | Hydration sequencing, failure handling, lifecycle reconciliation and device acceptance |
| Updating | Feed, verified APK download, installer flow and release publishing | Prompt dismissal, trustworthy tag/source provenance and real update-round-trip testing |
| Contacts/groups | Local contacts, group metadata and shared-content screens | Real identities, member selection, membership permissions and per-message sender identity |
| Calls | Simulated lifecycle, controls, notification and history UI | Correct direction/outcomes/timeouts; real calling requires signaling, media transport and background audio design |
| Stories | Creation, viewing, grouping and seen state | Media-ready timing/retry, durable files, real distribution and audience rules |

No accounts, remote messaging, push service, remote call media, encrypted local storage or OTA updates are documented prototype limits, not hidden defects. Group creation currently makes a self-only group, so wording or participant selection should make that expectation clear.

Choose the product direction explicitly. If this remains a local interaction demo, prioritize honest demo labels, reset/demo controls, accessibility and dependable local data. If it becomes a real messenger, first prove one-to-one delivery between two devices. More stories, call effects or OTA machinery should not precede that.

## Recommended work order

### 1. Protect data and releases

Fix D1–D5, U1 and R1 before another release. Add tests for a previously saved unopened forwarding target, storage rejection, partial startup failure, notification reply before hydration, duplicate retry after write failure, remembered update dismissal and mismatched event tags. Also retain empty chat lists and prevent stale reads.

Exit criteria: no mutation replaces unloaded history; failed durable writes remain retryable; initialization failure cannot overwrite healthy slices; release source/tag/version agree.

### 2. Make the existing app predictable

Fix scrolling, actual profile history, attachment ownership, foreground visibility, notification cleanup/privacy, story load timing and contrast. Standardize loading/empty/error states and disabled controls. Preserve recording guards and existing destructive-action confirmations.

Exit criteria: the same actions work after restart, offline media failures explain themselves, new messages do not steal scroll position, and Android Back returns to the expected screen.

### 3. Validate the shipped APK

Run the real release gate and test a shrunk release APK on Android hardware. Cover process death, notification reply/replay, permission denial and recovery, channel changes, keyboard image delivery, minimize/background camera behavior and installing over an older release. Record cold start, memory and scroll traces before performance changes.

The current 117 passing tests do not cover these integrated lifecycles. Add behavior tests around real controller boundaries rather than more source-pattern assertions. Native notification and downloader behavior also need targeted tests.

### 4. Build one real vertical slice if that is the goal

Implement authentication/identity, two-device one-to-one text messaging, durable outbox with client IDs, server acknowledgement, retry, incremental history sync and push routing. Verify offline-send then reconnect and duplicate delivery before expanding groups, stories or calling.

Next define media ownership/upload/download, local data protection, backup/export/recovery and account/device lifecycle. Define the threat model before promising encryption. Real calls are a separate substantial project, not a backend toggle.

## TLDR

Keep the stack and useful native work. Fix persistence, startup sequencing and updater/release integration first. The product needs fewer ambiguous states and stronger failure handling before it needs more features. The strongest next demonstration is trustworthy history and delivery, first locally and then between two devices.
