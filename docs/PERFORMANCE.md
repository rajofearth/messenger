# Performance

This file records what was changed for size and runtime, why, and how to re-measure it. It separates measured facts from structural reasoning. On-device numbers (startup, scroll timing, memory) have not been captured in this repository; APK size has been, and is in the first section.

## APK size

Measured: **43,537,847 bytes (41.52 MiB) before, 35,628,346 bytes (33.98 MiB)
after, a reduction of 18.2%** from enabling R8 minification and resource
shrinking. The breakdown is under "Measured APK size" below.

### Build configuration in `app.json`

The `expo-build-properties` plugin sets these under `android`:

| Option | Value | Effect |
| --- | --- | --- |
| `enableMinifyInReleaseBuilds` | `true` | R8/ProGuard shrinks and obfuscates Java and Kotlin. It is also a prerequisite for resource shrinking: the plugin throws at prebuild time if resource shrinking is enabled while minifying is not. |
| `enableShrinkResourcesInReleaseBuilds` | `true` | Gradle resource shrinking removes unused Android resources from the release APK. |
| `extraProguardRules` | keeps `expo.modules.keyboardmedia.**` and `expo.modules.systemnotifications.**` | The two local modules are reached through Expo's module registry and Android manifest components. Expo's default rules already keep module constructors and manifest components; these two rules pin the local modules' classes so renaming can never break a release build. |

The keep rules land in `android/app/proguard-rules.pro` between `@generated begin/end expo-build-properties` markers. That file is regenerated by `npm run android:prebuild` and must not be edited by hand.

### One ABI per release build

Both build paths pass `-PreactNativeArchitectures=arm64-v8a`:

- `scripts/android.mjs`, used by `npm run android:build` and `npm run android:install`: `gradlew.bat :app:assembleRelease -PreactNativeArchitectures=arm64-v8a --console=plain --max-workers=2`.
- `.github/workflows/release.yml`: `-PreactNativeArchitectures=arm64-v8a --console=plain --max-workers 4`.

The generated `android/gradle.properties` default is `reactNativeArchitectures=armeabi-v7a,arm64-v8a,x86,x86_64`, so without the flag the APK carries four sets of native libraries. The target device is a physical ARM64 phone (see the README); an x86-64 emulator needs its own ABI build. `--max-workers` is a build-time memory control, not an APK size one.

### Tunables deliberately left at their defaults

| Option | Current state | Why it was not changed |
| --- | --- | --- |
| `enableBundleCompression` | Not set in `app.json`. The React Native Gradle plugin's `ReactExtension` default is `false`, so the JS bundle is stored uncompressed and can be memory-mapped at startup. | The plugin's own comment documents the trade: skipping compression improves startup at the cost of a larger APK. Re-enabling it would shrink the file and give back startup time, and there is no on-device startup measurement to justify that. |
| `useLegacyPackaging` | Not set in `app.json`. The generated project keeps `expo.useLegacyPackaging=false` (also the fallback in `android/app/build.gradle`), so native libraries stay uncompressed and are not extracted at install. | Same trade as above, decided in favour of loading libraries directly from the APK. Compressed libraries would mean a smaller file and a slower install and first run. |
| `enablePngCrunchInReleaseBuilds` | Not set in `app.json`. The generated project keeps it on (`android.enablePngCrunchInReleaseBuilds=true`, and the Gradle fallback is `'true'`). | This is the setting that reduces asset size; turning it off would grow the APK to save build time only. |
| Metro `inlineRequires` | Not overridden. There is no `metro.config.js` in the repository, so bundling uses the Expo and Metro defaults. | Inline requires move module initialisation to first use, which affects startup and bundle layout. Changing it without before/after `adb shell am start -W` numbers would be a guess. |

### Measured APK size

Both figures below are the same working tree, the same Expo config and the same
`arm64-v8a`-only release build; the only difference is the `expo-build-properties`
options above. The APK is copied to `artifacts/messenger-local.apk` by
`npm run android:build`, and the numbers are that file's size in bytes.

| Build | Size | Change |
| --- | --- | --- |
| Before (minify and resource shrinking off) | 43,537,847 bytes (41.52 MiB) | - |
| After (minify and resource shrinking on) | 35,628,346 bytes (33.98 MiB) | **-7,909,501 bytes, -18.2%** |

Where the 7.5 MiB went, read from the archive with
`[System.IO.Compression.ZipFile]::OpenRead` and grouped by top-level entry:

| Entry group | Before | After | Notes |
| --- | --- | --- | --- |
| `classes*.dex` | 12.59 MiB in 4 files | 5.54 MiB in 2 files | R8 removed unreachable code and merged classes. This is almost the whole saving. |
| `resources.arsc` | 1.72 MiB | 1.36 MiB | Resource shrinking dropped unused resources. |
| `res/` | 3.45 MiB, 1316 entries | 3.36 MiB, 1015 entries | 301 unused resource files removed. |
| `lib/` | 20.60 MiB, 20 files | 20.60 MiB, 20 files | Unchanged: one ABI in both builds, and R8 does not touch `.so` files. |
| `assets/` | 2.69 MiB | 2.69 MiB | Unchanged: the JavaScript bundle and bundled fonts are already as small as the current bundling produces, and the bundle is stored uncompressed (see the tunables table). |

The same figures are worth quoting with their caveats: this is APK file size, not
installed size, and it says nothing about startup time. Minification adds build
time, and no on-device run has confirmed that the shrunk build behaves
identically, which is why the release notes ask for device testing.

## Runtime and list performance

### Lists

`ChatsScreen` and `ConversationScreen` both use `FlatList` with windowing props, and each row type is a separate memoised component.

| List | Props |
| --- | --- |
| `src/features/chats/ChatsScreen.tsx` | `initialNumToRender={10}`, `maxToRenderPerBatch={8}`, `windowSize={9}`, `removeClippedSubviews` |
| `src/features/conversations/ConversationScreen.tsx` | `initialNumToRender={12}`, `maxToRenderPerBatch={8}`, `windowSize={9}`, `scrollEventThrottle={32}` |

Rows are split out into `ChatRow.tsx` and `MessageRow.tsx`, both wrapped in `React.memo`. `ChatsScreen` memoises `keyExtractor` and `renderItem`; `ConversationScreen` memoises its rows through `groupMediaMessages` and its `renderItem` depends on those rows, dark mode, visibility and the callbacks. `App.tsx` also passes `key={chat.id}` to `ConversationScreen`, so switching conversations is a remount with fresh local state rather than a re-render of the previous thread.

### Why `getItemLayout` is not used

Neither list declares `getItemLayout`, so `FlatList` measures each row as it mounts. That is deliberate.

- Chat rows scale with the system font size. The row is text driven and React Native `Text` scales by default, so a hard-coded row height would be wrong for any user with a larger font scale, and wrong again if the accessibility setting changes while the app is running.
- Conversation rows are content dependent. One row can be a one-line text bubble; the next a media album of up to 50 items with a `+N` overlay, a reply snapshot, a deleted tombstone, or a video attachment with its own aspect ratio. There is no single height that fits all of them.
- `ConversationScreen` uses real sizes on purpose. It tracks whether the user is at the bottom (the `pinned` ref), calls `scrollToEnd` on `onContentSizeChange`, and chases the tail only while pinned. A fake `getItemLayout` height would give misleading content sizes, break that logic, and make `scrollToEnd` land in the wrong place.
- Nothing in either list jumps to a known index, which is the main capability `getItemLayout` enables. The chat list's reset after a search or tab change uses `scrollToOffset({ offset: 0 })`, which needs no layout estimate.

The cost of this choice is that each row is measured on first render. The benefit is correct layout at every font scale and content mix.

## Memory

### Images

`expo-image` renders message images (`MessageBubble.tsx`), media albums (`MediaAlbum.tsx`), the full-screen media viewer (`ConversationScreen.tsx`, `AlbumViewer.tsx`) and the shared-media grids (`ChatProfileShared.tsx`). Story media uses React Native's own `Image`, and video playback uses `expo-video`.

- `recyclingKey={message.id}` (in `MessageBubble.tsx`, `MediaAlbum.tsx`, `AlbumViewer.tsx` and `ChatProfileShared.tsx`) tells `expo-image` that a recycled view now shows a different image, so the view and its decode can be reused instead of holding a second image while the old one is still mounted.
- `cachePolicy="memory-disk"` is set on the two media grid callers (`MediaAlbum.tsx` and `ChatProfileShared.tsx`); other `expo-image` callers use the default policy. The memory tier makes scrolling back over already-seen media cheap, and the disk tier keeps the memory tier from having to hold everything.

### Source URLs are size parameterised

`src/domain/data.ts` exposes `image(id, width, quality = 80)`, with `avatar(id) = image(id, 200)` and `media(id) = image(id, 1080)`. Requesting the size actually displayed keeps both the download and the decoded bitmap small. Avatars are 200 px wide, enough for a 56 dp circle on a 3x display; story and message media are 1080 px, the size the full-screen viewer needs. A full-resolution URL would make every avatar decode cost many times the memory for pixels that are never shown, and the comment on the helper ties the choice to exactly that.

### Avatars in the notification pipeline

Android notification image decoding accepts `file://` and `content://` URIs only, and it samples an image down to a thumbnail (stated in `modules/system-notifications/README.md`). Contact avatars are remote Unsplash URLs, so `src/data/avatars.ts` downloads each one once into `Paths.cache/avatars` and caches the local URI in memory (maximum 256 entries, pruned folder beyond 240 files). `useMessageNotifications` and `useCallNotifications` await `localAvatarUri` and pass the local file into the native payload. That keeps the notification path off the network after the first use, keeps the decoded image small, and makes later updates to the same notification cost no download. `warmAvatars` pre-downloads the avatars of the first 8 conversations two at a time so a ringing call or a notification usually has a local image ready.

### Lazy per-conversation history

Only conversations opened since launch have their messages in memory (the `messages` record in `useMessenger`). The full history is never loaded at startup, and `thread()` single-flights concurrent opens, so a double tap cannot load the same thread twice. Persisted messages are split per chat id, so a send writes one thread key plus the chat list, and the seeded threads from `seedMessages(chat)` are generated on demand and only stored once a conversation is touched.

## Startup and JavaScript

- **Per-slice persistence.** The whole app state is never re-serialised. Each slice effect compares identity with the last value it wrote and returns early when nothing changed, and the message effect walks the per-thread map and writes only threads whose array identity changed. A send serialises one conversation and the chat list.
- **Coalesced writes.** `createStore` queues writes in a `Map` keyed by the full storage key, so a burst of state changes for the same key collapses to the newest value and the queue drains in order. Memory is updated synchronously inside `save`, so no read ever waits for disk.
- **500-line modules.** The limit in `scripts/architecture.test.mjs` is a maintainability rule. Small files stay navigable and keep the layer checks meaningful. It is not a measured runtime win: imports compile away, and the only real cost of splitting a file is developer time.

## How to measure

Run from the repository root.

| Command | What it gives | What it does not give |
| --- | --- | --- |
| `npm test` | Unit tests, including cache TTL, LRU and single-flight (`src/data/cache.test.mjs`) and notification payload mapping (`src/notifications/payloads.test.mjs`), plus the architecture rules. No device needed. | Nothing about runtime performance. |
| `npm run typecheck` | Type safety. | No runtime information. |
| `npx expo export --platform android --output-dir artifacts/preview-bundle --max-workers 1` | Builds the JS bundle and prints its size; catches Metro-only failures. The release workflow uses `--max-workers 2`. | Not the APK size. Gradle adds assets and native libraries later. |
| `npm run android:build` | Builds the release APK for `arm64-v8a` and copies it to `artifacts/messenger-local.apk`. | No timing or memory numbers, and the build takes minutes. |
| `(Get-Item artifacts\messenger-local.apk).Length` | APK size in bytes (PowerShell). In `cmd`, `for %f in (artifacts\messenger-local.apk) do @echo %~zf` prints the same. | Does not say where the size went. |
| Any zip tool, for example `unzip -l artifacts/messenger-local.apk` | The largest entries: `assets/index.android.bundle`, `lib/arm64-v8a/*.so` and resources. The release workflow already prints the arm64 library count and confirms the bundle exists. | No attribution beyond file sizes. |

### Needs a physical device

- Cold start time: `adb shell am start -W -n com.yashraj.messenger/.MainActivity`, with the device otherwise idle.
- Scroll smoothness and frame timing: Android Studio profiler or `perfetto`, while scrolling the chat list and a media-heavy conversation.
- Memory: `adb shell dumpsys meminfo com.yashraj.messenger` after a cold start, after opening several conversations, and after scrolling a media album, to check that history and image memory really are bounded.
- Notification behaviour and keyboard media delivery: the checklists in `modules/system-notifications/README.md` and `modules/keyboard-media/README.md` both say a rebuilt app on real hardware is required, and a real IME for keyboard media. Neither has been verified on a device in this repository.
- Install and update size, which differ from the APK file size.

There is no automated performance harness here. No baseline for startup, frame timing or memory was captured during setup, so any number quoted later needs the same command run twice, before and after the change.

## Why some things were not done

- **FlashList was not added.** The lists hold nine seeded chats and threads of a handful of messages. A new dependency and a new list API would not pay for themselves at this volume, and there is no measured jank to justify the swap.
- **No deep virtualisation experiments.** No fixed row heights, no `getItemLayout`, no cell-recycling tricks beyond what `FlatList` and `expo-image` already provide. The reasons are in the `getItemLayout` section: variable font scale and content-dependent rows.
- **Memory was not measured on device.** No phone was connected during setup, as the README states. Everything in the Memory section is structural reasoning, not a measurement. The avatar folder lives in `Paths.cache`, which Android can clear at any time, so even its disk size is not a fixed number.
- **No further size options were enabled.** Bundle compression, legacy packaging and PNG crunching are at the defaults described above. Changing them trades startup or install behaviour for file size, and there are no on-device numbers to justify that trade.
- **No JS-level profiling.** Hermes is on (`hermesEnabled=true` in the generated `android/gradle.properties`), but no sampling or tracing run has been recorded in this repository.
