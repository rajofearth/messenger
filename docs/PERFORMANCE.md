# Performance

This file records what was changed for size and runtime, why, and how to re-measure it. It separates measured facts from structural reasoning. On-device numbers (startup, scroll timing, memory) have not been captured in this repository; APK size has been, and is in the first section.

## APK size

Measured: **43,537,847 bytes (41.52 MiB) before any size work, 14,376,582 bytes
(13.71 MiB) in v0.1.1** — 67.0% smaller, in nine measured stages. R8
minification and resource shrinking took the APK to 35,628,346 bytes
(33.98 MiB). Compressing the native libraries, removing the unused camera
barcode scanner and trimming bundled fonts took it to 15,680,499 bytes
(14.95 MiB). Keeping only English resources brought it to 14,926,315 bytes
(14.23 MiB), the in-app updater added 32,964 bytes for 14,959,279 bytes
(14.27 MiB), the device-scheme module added 3,720 for 14,962,999 bytes
(14.27 MiB), and the audit fixes added 4,136 bytes for 14,967,135 bytes
(14.27 MiB). The first Convex-backed chat build reached 15,516,415 bytes
(14.80 MiB). The mobile polish and size pass then removed 1,140,945 bytes,
ending at 14,375,470 bytes (13.71 MiB), 2.29 MiB below the 16 MiB gate. The
v0.1.1 sign-in copy added 1,112 bytes to the local build, for 14,376,582 bytes
(13.71 MiB), still 2.29 MiB below the gate. The published v0.1.1 APK is
14,376,546 bytes, 36 bytes below the local gate build. Upload progress and
story viewers then added 8,208 bytes to the local gate build, for 14,384,754
bytes (13.72 MiB), still 2.28 MiB below the gate. The stage table and the
per-entry breakdown are under "Measured APK size".

The 2026-10-24 media regression **development** APK
`0.1.1-dev.20261024.124711` is **14,418,602 bytes (13.75 MiB)**, up **4,624 bytes**
from dev release `dev-1792814710` (14,413,978 bytes). The focused changes add
verified gallery-export checks, inline save status, first-video-frame telemetry
and a compact update prompt; native dependencies and ABIs are unchanged. The
APK passed all 11 slim-build checks and remains below the 16 MiB budget. This is
a local build measurement, not a claim that device acceptance has passed.

### Build configuration in `app.json`

The `expo-build-properties` plugin sets these under `android`:

| Option | Value | Effect |
| --- | --- | --- |
| `enableMinifyInReleaseBuilds` | `true` | R8/ProGuard shrinks and obfuscates Java and Kotlin. It is also a prerequisite for resource shrinking: the plugin throws at prebuild time if resource shrinking is enabled while minifying is not. |
| `enableShrinkResourcesInReleaseBuilds` | `true` | Gradle resource shrinking removes unused Android resources from the release APK. |
| `useLegacyPackaging` | `true` | Native libraries are stored deflate-compressed instead of stored as-is, and `android:extractNativeLibs="true"` is set in the merged manifest, so Android extracts them at install time. The libraries compress between 1.9× and 4×, which makes this the single largest saving; the trade is a slower install and first launch. |
| `extraProguardRules` | keeps `expo.modules.keyboardmedia.**`, `expo.modules.systemnotifications.**`, `expo.modules.appupdater.**` and `expo.modules.devicescheme.**`, and adds `-dontwarn com.google.mlkit.**` plus `-dontwarn com.google.android.gms.tasks.**` | The keep rules pin the four local modules so renaming can never break a release build. The `-dontwarn` rules are what let the release build compile with the MLKit barcode classes absent; see the barcode section below. |

These rules land in `android/app/proguard-rules.pro` between `@generated begin/end expo-build-properties` markers. That file is regenerated by `npm run android:prebuild` and must not be edited by hand. `npm run android:build` regenerates the Android project only when `android/` is missing, so a configuration change needs an explicit `npm run android:prebuild` first.

### R8 optimiser

`plugins/withOptimizingR8.js` changes the release build's default ProGuard file from `proguard-android.txt` to `proguard-android-optimize.txt`, and removes the template's Reanimated keep rule (Reanimated is not a dependency). The template file contains `-dontoptimize`; the optimized one enables inlining, class merging and dead-code removal. The plugin edits only generated files, accepts an already-optimized `build.gradle` on a second prebuild, and throws if neither file is present.

Measured with real release APKs of this branch (arm64-v8a only, as the release workflow builds it):

| Build | Bytes | MiB | Delta |
| --- | ---: | ---: | ---: |
| Previous development APK `dev-1792832501` | 14,424,194 | 13.76 | - |
| Same source, R8 optimiser off | 14,474,042 | 13.80 | +49,848 |
| Same source, R8 optimiser on (shipping) | 13,161,063 | 12.55 | -1,312,979 |

The optimiser alone removes 1,312,979 bytes (9.07%) from the same JavaScript bundle and resources: the bundle is byte-identical in both APKs, and the difference is dex size (7.93 MiB in one dex versus 11.90 MiB in two). The integrated build is 1,263,131 bytes (8.76%) smaller than the previous development APK, 3.45 MiB under the 16 MiB budget and 2.45 MiB under the 15 MiB shipping line. `npm run release:check` passed all 11 checks with no warnings on the final APK. The release workflow now keeps `mapping-<version>.txt` beside the APK (release asset and workflow artifact), and the dev release script uploads it too, so an obfuscated stack trace can be read.

The development build `dev-1792920281` was installed on the user's Android device and the user confirmed on 2026-10-25 that the app works: every screen, media path, auth flow, notification and the in-app updater behaved correctly. That is the device acceptance for the R8 build and the updater changes; the individual fault-injection cases in the PR checklist were not separately scripted.

### The camera barcode scanner is not bundled

`expo-camera` links MLKit's barcode scanner by default: `libbarhopper_v3.so`
(4,946,720 bytes), 880,888 bytes of bundled TensorFlow Lite models and their
Java classes under `com.google.mlkit.*` and `com.google.android.gms.*`. This app
has no barcode feature, so all of it was removed:

- `package.json` lists `expo-camera` under
  `expo.autolinking.android.buildFromSource`. Expo ships the module as a
  prebuilt AAR in a local Maven repository, and that AAR depends on MLKit at
  runtime, so Gradle has to build the module from `node_modules` before the
  module's own build toggle can take effect.
- `plugins/withBarcodeScannerDisabled.js` writes
  `expo.camera.barcode-scanner-enabled=false` into `android/gradle.properties`.
  That file is regenerated by every prebuild, so the value can only come from a
  config plugin. The module then compiles its MLKit dependencies as
  `compileOnly` and they are not packaged.
- The `-dontwarn` rules in `app.json` cover the classes that are missing at R8
  time once the dependencies are gone; without them the release build fails.

The barcode paths stay unreachable at runtime: the camera creates a barcode
analyzer only when JavaScript asks for barcode scanning, and the module's
availability check is a `Class.forName` probe that now reports the scanner as
unavailable. Preview, photo capture and video recording are unaffected, and the
manifest keeps `android.permission.CAMERA`.

### Fresco decoders and LogBox are not packaged

Every image call site now uses `expo-image`; an architecture test fails if a
source file imports React Native's Fresco `Image` again. That makes the Fresco
GIF and WebP decoders unused, so `plugins/withSizeTunables.js` writes
`expo.gif.enabled=false`, `expo.webp.enabled=false` and
`expo.webp.animated=false` into the generated `android/gradle.properties`.
Expo Image still uses Glide for GIF and WebP, so animated media keeps working.

The same plugin sets `android.r8.optimizedResourceShrinking=true`, which lets
resource shrinking run against R8's optimized graph as well as its unoptimized
one. Separately, `package.json` excludes the dev-only `@expo/log-box` package
from Android autolinking; it is not reachable in a release build and no longer
contributes native code or dex.

The combined result is 17 native libraries instead of 19, 5,164,570 bytes of
compressed dex instead of 5,529,914, and a 171,316-byte `resources.arsc` instead
of 522,336. The JavaScript bundle grew 17,460 bytes over the same pass for the
UX and accessibility work; it is still stored uncompressed at 2,058,288 bytes.

### Fonts and icons are trimmed to what the app uses

- `src/ui/StartupGate.tsx` loads four DM Sans weights: 400, 500, 600 and 700.
  It used to import them from the package root, whose `index.js` requires all
  eighteen weights. Direct imports from
  `@expo-google-fonts/dm-sans/400Regular` and its siblings, plus `useFonts` from
  `expo-font`, make Metro pull in only the faces the app renders. The 600 face
  added by the UX pass costs 29,863 stored bytes.
- Every file that imported `{ Ionicons }` from `@expo/vector-icons` now imports
  the Ionicons module directly. The package root re-exports every icon family,
  which bundled each family's glyph map and font; MaterialCommunityIcons alone
  was 1.31 MiB. Ionicons is the only family the UI uses.

The bundled `.ttf` resources fell from 38 files, 2,609,365 stored bytes (about
2.5 MiB), to 6 files, 333,243 stored bytes (about 0.32 MiB). The six are the
four DM Sans weights, Ionicons and a 2 KiB Roboto resource that arrives from
another dependency.

### Only English resources are packaged

Every AndroidX, Material and Play Services library ships its interface strings
translated into around a hundred locales. Resource shrinking leaves them alone
because they are reachable from the merged resources, so about a hundred
languages sat in `resources.arsc` even though the app's own UI is
English-only. `plugins/withEnglishOnlyResources.js` writes `resConfigs "en"`
into `defaultConfig` in the generated `android/app/build.gradle`, which tells
AAPT2 to keep English and the default configuration only.

The resource table fell from 1,284,976 to 515,120 stored bytes and the APK
from 15,680,499 to 14,926,315 bytes (14.23 MiB). `resConfigs` filters locale
qualifiers only: density, night mode, screen size, orientation and
layout-direction resources are untouched, so adaptive icons, `values-night`
and `ldrtl` layouts keep working. The app itself has no translated strings to
lose.

### One ABI per release build

Both build paths pass `-PreactNativeArchitectures=arm64-v8a`:

- `scripts/android.mjs`, used by `npm run android:build` and `npm run android:install`: `gradlew.bat :app:assembleRelease -PreactNativeArchitectures=arm64-v8a --console=plain --max-workers=2`.
- `.github/workflows/release.yml`: `-PreactNativeArchitectures=arm64-v8a --console=plain --max-workers 4`.

The generated `android/gradle.properties` default is `reactNativeArchitectures=armeabi-v7a,arm64-v8a,x86,x86_64`, so without the flag the APK carries four sets of native libraries. The target device is a physical ARM64 phone (see the README); an x86-64 emulator needs its own ABI build. `--max-workers` is a build-time memory control, not an APK size one.

| Option | Current state | Why it was not changed |
| --- | --- | --- |
| `enableBundleCompression` | Not set in `app.json`. The React Native Gradle plugin's `ReactExtension` default is `false`, so the JS bundle is stored uncompressed (2,058,288 bytes) and can be memory-mapped at startup. | The plugin's own comment documents the trade: skipping compression improves startup at the cost of a larger APK. ## Runtime and list performance

### Lists

`ChatsScreen` and `ConversationScreen` both use `FlatList` with windowing props, and each row type is a separate memoised component.

| List | Props |
| --- | --- |
| `src/features/chats/ChatsScreen.tsx` | `initialNumToRender={10}`, `maxToRenderPerBatch={8}`, `windowSize={9}`, `removeClippedSubviews` |
| `src/features/conversations/ConversationScreen.tsx` | `initialNumToRender={12}`, `maxToRenderPerBatch={8}`, `windowSize={9}`, `scrollEventThrottle={32}` |

Rows are split out into `ChatRow.tsx` and `MessageRow.tsx`, both wrapped in `React.memo`. `ChatsScreen` memoises `keyExtractor` and `renderItem`; `ConversationScreen` memoises its rows through `groupMediaMessages` and its `renderItem` depends on those rows, dark mode, visibility and the callbacks. `App.tsx` also passes `key={chat.id}` to `ConversationScreen`, so switching conversations is a remount with fresh local state rather than a re-render of the previous thread.

### Why `getItemLayout` is not used

Neither list declares `getItemLayout`, so `FlatList` measures each row as it mounts. That is deliberate.

- Chat rows scale with the system font size. The row is text driven and React Native `Text` scales by default, so a hard-coded row height would be wrong for any user with a larger font scale, and wrong again if the accessibility setting changes while the app is running.
- Conversation rows are content dependent. One row can be a one-line text bubble; the next a media album of up to 50 items with a `+N` overlay, a reply snapshot, a deleted tombstone, or a video attachment with its own aspect ratio. There is no single height that fits all of them.
- `ConversationScreen` uses real sizes on purpose. It tracks whether the user is at the bottom (the `pinned` ref), calls `scrollToEnd` on `onContentSizeChange`, and chases the tail only while pinned. A fake `getItemLayout` height would give misleading content sizes, break that logic, and make `scrollToEnd` land in the wrong place.
- Nothing in either list jumps to a known index, which is the main capability `getItemLayout` enables. The chat list's reset after a search or tab change uses `scrollToOffset({ offset: 0 })`, which needs no layout estimate.

The cost of this choice is that each row is measured on first render. The benefit is correct layout at every font scale and content mix.

## Memory

### Images

`expo-image` renders every image surface, including message images (`MessageBubble.tsx`), media albums (`MediaAlbum.tsx`), the full-screen media viewer (`ConversationScreen.tsx`, `AlbumViewer.tsx`), the shared-media grids (`ChatProfileShared.tsx`) and story media (`StoryMedia.tsx`). Video playback uses `expo-video`.

- `recyclingKey={message.id}` (in `MessageBubble.tsx`, `MediaAlbum.tsx`, `AlbumViewer.tsx` and `ChatProfileShared.tsx`) tells `expo-image` that a recycled view now shows a different image, so the view and its decode can be reused instead of holding a second image while the old one is still mounted.
- `cachePolicy="memory-disk"` is set on the two media grid callers (`MediaAlbum.tsx` and `ChatProfileShared.tsx`); other `expo-image` callers use the default policy. The memory tier makes scrolling back over already-seen media cheap, and the disk tier keeps the memory tier from having to hold everything.

The device media picker uses a stricter path than the conversation media grids.
`src/features/media/MediaPickerThumbnail.tsx` asks the Android-only
`modules/media-thumbnails` Expo module for a `ContentResolver.loadThumbnail`
JPEG capped at 384 pixels. The result is cached in the app cache and reused by
the JavaScript single-flight cache across picker openings, so the grid and album
sheet never decode the original camera file while scrolling. Full asset URIs
are resolved only after selection or when the user opens the preview. The
photo preview resolves the full asset after the thumbnail. Only the active
carousel page mounts a video player; it autoplays with audio and exposes native
elapsed/total time and scrubbing inside the safe-area-bounded media stage, away
from the action footer. Inactive videos use JPEG posters, not video URIs in the
image decoder. Expo's `useVideoPlayer` owns player release; there is no separate
pause-on-unmount callback that could run after the native object was released.

This is structural protection, not an on-device frame-time measurement. A
physical Android run is still required to confirm the exact scroll frame rate
and the close path on the target phone.

### Development telemetry

Development APKs collect only coarse interaction and timing events through
`src/services/devTelemetry.ts`. The queue records event names, timestamps,
durations, counts, media kind, coarse JS heap usage when the runtime exposes it,
and error codes; it never records media URIs, captions, filenames or image/video
contents. Events are batched into the development Convex deployment's
`devTelemetry` table and flushed after 25 events, after a short idle delay, or
when the app backgrounds. Production builds do not enqueue or send these
events. The `devTelemetry.listRecent` query makes the latest session data
available from the development Convex dashboard after a device test.

`media_preview_video_first_frame` measures the first rendered frame, separately
from thumbnail URI resolution. Gallery exports record `gallery_save_verified`
only after checking the public Android file's byte count, media dimensions and
album membership; failures record a bounded stage/error code, never an exception
message or path. Story saves also record `story_save_completed` or
`story_save_failed` with elapsed time. These are diagnostics, not native crash
capture, and the in-memory queue can lose events when a process crashes.

The local regression harness executes the installed Expo shared-object lifecycle
and catches a pause-after-release on video unmount. Gallery and update-prompt
tests mock native APIs; they do not establish visibility in a manufacturer's
Gallery or visual fit on hardware. Use [the device checklist](MEDIA_TESTING.md)
before calling those runtime behaviours verified.

### Remote media is downloaded once

Convex storage returns a signed URL only after the conversation membership check. `src/services/mediaCache.ts` downloads each received file once into `Paths.document/messenger-media`, named after the message or story id, so reopening a thread, prefetching a story or saving an album copy does not download it again. The signed URL stays as the fallback when a download fails. Images keep the sender's aspect ratio; no server-side resize is performed, and `expo-image` decodes at the displayed size.

### Avatars in the notification pipeline

Android notification image decoding accepts `file://` and `content://` URIs only, and it samples an image down to a thumbnail (stated in `modules/system-notifications/README.md`). Contact avatars are remote profile URLs, so `src/data/avatars.ts` downloads each one once into `Paths.cache/avatars` and caches the local URI in memory (maximum 256 entries, pruned folder beyond 240 files). `useMessageNotifications` and `useCallNotifications` await `localAvatarUri` and pass the local file into the native payload. That keeps the notification path off the network after the first use, keeps the decoded image small, and makes later updates to the same notification cost no download. `warmAvatars` pre-downloads the avatars of the first 8 conversations two at a time so a ringing call or a notification usually has a local image ready.

### Lazy per-conversation history

Only the selected conversation's thread is queried (`api.chat.listMessages`, newest 100 messages). `useRemoteCache` hydrates the inbox, stories, settings and call history at launch, while `useRemoteThreadMedia` stores an opened thread and its downloaded files. Persisted messages are split per chat id, so a send writes one thread key plus the chat list, not the whole app state.

## Startup and JavaScript

- **Per-slice persistence.** The whole app state is never re-serialised. Each slice effect compares identity with the last value it wrote and returns early when nothing changed, and the message effect walks the per-thread map and writes only threads whose array identity changed. A send serialises one conversation and the chat list.
- **Coalesced writes.** `createStore` queues writes in a `Map` keyed by the full storage key, so a burst of state changes for the same key collapses to the newest value and the queue drains in order. Memory is updated synchronously inside `save`, so no read ever waits for disk.
- **500-line modules.** The limit in `scripts/architecture.test.mjs` is a maintainability rule. Small files stay navigable and keep the layer checks meaningful. It is not a measured runtime win: imports compile away, and the only real cost of splitting a file is developer time.

## How to measure

Run from the repository root.

| Command | What it gives | What it does not give |
| --- | --- | --- |
| `npm test` | Unit tests, including cache TTL, LRU and single-flight (`src/data/cache.test.mjs`) and notification payload mapping (`src/notifications/payloads.test.mjs`), plus the architecture rules. No device needed. | Nothing about runtime performance. |
| `npm run typecheck` | Type safety. | No runtime information. |
| `npx expo export --platform android --output-dir artifacts/preview-bundle --max-workers 1` | Builds the JS bundle and prints its size; catches Metro-only failures. The release workflow uses `--max-workers 2`. | Not the APK size. Gradle adds assets and native libraries later. |
| `npm run android:build` | Builds the release APK for `arm64-v8a` and copies it to `artifacts/messenger-local.apk`. | No timing or memory numbers, and the build takes minutes. |
| `(Get-Item artifacts\messenger-local.apk).Length` | APK size in bytes (PowerShell). In `cmd`, `for %f in (artifacts\messenger-local.apk) do @echo %~zf` prints the same. | Does not say where the size went. |
| Any zip tool, for example `unzip -l artifacts/messenger-local.apk` | The largest entries: `assets/index.android.bundle`, `lib/arm64-v8a/*.so` and resources. The release workflow already prints the arm64 library count and confirms the bundle exists. | No attribution beyond file sizes. |

### Needs a physical device

- Cold start time: `adb shell am start -W -n com.yashraj.messenger/.MainActivity`, with the device otherwise idle.
- Scroll smoothness and frame timing: Android Studio profiler or `perfetto`, while scrolling the chat list and a media-heavy conversation.
- Memory: `adb shell dumpsys meminfo com.yashraj.messenger` after a cold start, after opening several conversations, and after scrolling a media album, to check that history and image memory really are bounded.
- Notification behaviour and keyboard media delivery: the checklists in `modules/system-notifications/README.md` and `modules/keyboard-media/README.md` both say a rebuilt app on real hardware is required, and a real IME for keyboard media. Neither has been verified on a device in this repository.
- A real update round trip: publish a newer build, let an older build download it, cancel once, toggle the "install unknown apps" permission both ways, finish Android's installer, and check that the app reopens on the new version with its local state intact and the cached APK removed.
- Install and update size, which differ from the APK file size.

There is no automated performance harness here. No baseline for startup, frame timing or memory was captured during setup, so any number quoted later needs the same command run twice, before and after the change.

## Why some things were not done

- **FlashList was not added.** A new dependency and a new list API would not pay for themselves without measured jank, and the thread is capped at the newest 100 messages.
- **No deep virtualisation experiments.** No fixed row heights, no `getItemLayout`, no cell-recycling tricks beyond what `FlatList` and `expo-image` already provide. The reasons are in the `getItemLayout` section: variable font scale and content-dependent rows.
- **Memory was not measured on device.** No phone was connected during setup, as the README states. Everything in the Memory section is structural reasoning, not a measurement. The avatar folder lives in `Paths.cache`, which Android can clear at any time, so even its disk size is not a fixed number.
- **Bundle compression stays off.** Legacy packaging is now on and PNG crunching remains at its default on; both are described above. `enableBundleCompression` is the one size lever still unused: it would save roughly 1.0 MiB, but every start would decompress the JavaScript bundle instead of mapping it. With the APK at 13.71 MiB there is no reason to take that trade without on-device startup numbers.
- **No JS-level profiling.** Hermes is on (`hermesEnabled=true` in the generated `android/gradle.properties`), but no sampling or tracing run has been recorded in this repository.
- **JDK 21 was not adopted, and JDK 26/27 are not options.** The build runs on JDK 17, which is also Android Gradle Plugin 8.12's target. An app-wipe build on JDK 21 took 88.1s against 65.7s on JDK 17 over an identical task set on this Windows-on-ARM machine (one run each; x86 Linux numbers elsewhere differ), so 21 buys nothing here. JDK 26 needs Gradle 9.4 and JDK 27 needs Gradle 9.8; the wrapper ships 9.3.1, which supports JVM 17-25. The measured win was caching, which is JDK-independent.
